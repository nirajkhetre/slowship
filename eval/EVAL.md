# slowship: an honest evaluation

Every number below was measured on 20–21 Oct 2026 with `eval/run.mjs` and the code in `src/` as it stands, on one
machine: Intel i5-12450HX, 16 GB RAM, RTX 4050 Laptop (6 GB), Windows 11, Node 24.20.0, Ollama with `gemma4:e2b`
(Q4_K_M). Nothing was estimated. Where something could not be measured, this file says so and says why.

The runner never executes a sample. It downloads bytes, checks their git hashes, and hands the folders to slowship's
own scan path (`scan.checkItems`), which only reads files as text.

## In short

| | rules only | rules + local model |
|---|---|---|
| Skills (MalSkillBench, 100 malicious + 100 benign): **hold** | precision 85.7%, recall 12.0%, 2 false holds | precision 81.3%, recall 13.0%, 3 false holds (both runs) |
| Skills: **hold or review** | precision 75.7%, recall 53.0%, 17 false alarms | precision 80.0–80.5%, recall 33.0–36.0%, 8–9 false alarms (two runs) |
| npm packages, malicious | **not measured** (no download approved; see section 2) | not measured |
| npm packages, 174 installed, assumed benign | 0 holds, 12 reviews (6.9%); 18 (10.3%) before the description and fixed-command rules | 0 holds, 3 reviews (1.7%) |
| Full run of D:/sloth-test (273 items), first time | 29.0 s | 319.9 s |
| Same run again, nothing changed | 1.8 s | 2.1 s |

What it means, plainly:

- When slowship says **hold**, it is usually right: 12 of 14 holds (rules) and 13 of 16 holds (model) were real
  malware. But hold catches only about 1 malicious skill in 8.
- Counting **review** as well catches about half (rules) or a third (model) of the malicious skills. Most of the
  rest are attacks written as plain English in SKILL.md, or code inside markdown code blocks, and slowship doesn't read
  those as code. Details in [why it misses](#14-why-it-misses).
- The local model halves the false alarms, but it also lets through 17 to 20 more malicious skills, because those attacks
  come with a description written to make their behaviour look expected.
- Rereading an unchanged machine takes about 2 seconds instead of 5 minutes, because results are cached by content.

### How sure are these numbers?

100 malicious and 100 benign skills can't pin a rate to the decimal point. Each rate has a range it is 95% likely to
sit in (a Wilson interval, printed by `eval/run.mjs`; worked out on 22 Oct from the stored results, no new runs):

| | rules only | rules + model |
|---|---|---|
| malicious skills held | 12 of 100, so 7–20% | 13 of 100, so 8–21% |
| holds that were real malware | 12 of 14, so 60–96% | 13 of 16, so 57–93% |
| malicious skills held or flagged for review | 53 of 100, so 43–62% | 36 and 33 of 100, so 27–46% and 25–43% |
| benign skills flagged (false alarms) | 17 of 100, so 11–26% | 9 and 8 of 100, so 5–16% and 4–15% |
| benign npm packages flagged | 12 of 174, so 4–12% (18, so 7–16%, before the description and fixed-command rules) | 3 of 174, so 1–5% |

The ranges overlap, but that alone doesn't settle anything here, because both columns score the *same* 200 skills. So
`eval/run.mjs compare` lines the two runs up skill by skill and counts which way each changed verdict went:

| | flagged by rules, not with the model | flagged with the model, not by rules | chance of a split this lopsided |
|---|---|---|---|
| malicious, first model run | 19 | 2 | 0.0002 |
| malicious, second model run | 22 | 2 | 0.00004 |
| benign, first model run | 9 | 1 | 0.02 |
| benign, second model run | 9 | 0 | 0.004 |
| first model run against the second (malicious, benign) | 3, 1 flagged only in the first | 0, 0 flagged only in the second | 0.25, 1.0 |

So both effects of the model are real, not luck: it lets real attacks through, and it removes real false alarms. The
two model runs differ from each other by a few skills with no direction to it, which is the run-to-run noise noted in
section 1.2. The two rules-only runs were identical.

## 1. Skills: MalSkillBench

### 1.1 Data

- Source: [lxyeternal/MalSkillBench](https://github.com/lxyeternal/MalSkillBench), commit `06e083125d5ec5dd7a189dfedadfe587a70635b9`
  (10 Jun 2026), folders `Dataset/Skills/malware` (3,944 skills) and `Dataset/Skills/benign` (4,000 skills).
- Subset: from each folder, the 100 skill folders whose names have the lowest SHA-256 (UTF-8 name, hex order). Same
  command, same 200 skills. That is 544 files and 2.8 MB, stored in `D:/slowship-eval/malskillbench`.
- The 100 malicious skills, by the dataset's own labels: 36 code injection (CI), 20 mixed (MIXED), 28 prompt injection
  (PI), all generated by the benchmark's pipeline and verified at runtime, plus 16 "wild" skills collected from public
  registries.
- All 544 files were still on disk and unchanged when scored, and again after the last run. Windows Defender logged
  3 detections while the second model run was reading the samples (the log doesn't name the files without admin
  rights) and briefly refused reads while it scanned, but no file was removed or changed.

### 1.4 Why it misses

All 47 rules-only misses, by cause. These are gaps in what slowship reads, not bad luck.

1. **Prompt injection written as prose (20).** SKILL.md has four narrow phrase rules: hide something from the user,
   ignore other instructions, download and run a script, send local data to a URL. The benchmark's PI attacks mostly
   do other things: role hijack (3 skills), safety bypass (4), leaking the system prompt (3), goal hijack (1),
   content manipulation (2), resource abuse hidden in text (4), and others (3). None of them use the phrases the rules
   look for.
2. **The wild campaign (15 of 16 wild skills).** All 15 have the same shape: a "prerequisites" section telling you to
   install a helper first. 9 do it with a base64 string piped into `bash`, so the words `curl` or `wget` never appear
   in plain text, and the download-and-run rule needs them. The other 6 point you to a password-protected zip to run,
   or a paste site whose script you're told to paste into your terminal. No rule covers either. The one wild skill
   that was flagged got there because its scripts make network requests, not because the trick was spotted.
3. **Code inside markdown code blocks (8 of 8).** The CI "inline code block" attacks put the payload in a fenced
   code block in SKILL.md, for the agent to copy and run. slowship reads `.md` files only with the phrase rules
   above, never as code.
4. **TypeScript (2).** `design-system-patterns` and `openevidence-sdk-patterns__MIXED_B1` carry their payload in
   `.ts` files. slowship parses only `.js`, `.cjs` and `.mjs`, plus Python and shell scripts line by line.
5. **Ransomware in scripts (2).** `list-npm-package-content` (shell) and `modal__MIXED_B7` (Python) prepare to
   encrypt your files. No rule looks for bulk encryption or deletion.

### 1.5 What the model changes (first run)

- It moved 19 malicious skills from review down to notable, by calling their network or program-running code
  "expected". MalSkillBench builds each attack inside a believable skill, so the description really does make that
  code look normal. Asking "does this match what it says?" doesn't help when the attacker wrote what it says.
- It moved 9 benign skills from review down to notable, for the same reason, which is the intended effect.
- It raised one malicious skill (`crdb-change__MIXED_B2`) and one benign skill (`molt-chess`, a game client that
  sends its own API token to its own server) from review to hold, by calling a token sent over the network
  unexpected.
- It can't lower a code combination: two benign skills stayed at review on a token + network combination even though
  the model said the token use matched their description. That is by design.

### 1.6 False alarms

Rules only (17): two holds and 15 reviews.

- `gateway-monitor-auto-restart`, **hold**, persistence: its setup script adds a cron job. Restarting a service on a
  schedule is the skill's whole job, and a combination can't be talked down by the model.
- `skill-security-audit`, **hold**, credential file + network: a security-audit skill whose docs list the attack
  phrases it looks for ("ignore all previous instructions", reading `~/.ssh/id_rsa`). The phrase rules can't tell an
  example of an attack from an instruction.
- 8 reviews for network requests alone in a script (`antigravity-balance`, `beszel-check`, `bvg-route`,
  `crypto-levels`, `fitbit-analytics`, `qwen-tts`, `web-search-instant`, `web-search-plus`).
- 3 reviews for an API token read next to a network request (`afame`, `clawdcasino`, `molt-chess`).
- 3 reviews for running a program (`george`, `ms365`, `video-subtitles`).
- 1 review for documenting a `curl … | sh` install (`openclaw-skill-auditor`).

With the model, first run (9): the two holds above, plus `molt-chess` raised to hold; reviews that stayed for `afame`,
`clawdcasino`, `ms365`, `openclaw-skill-auditor` and `qwen-tts`; and `tech-news-digest`, raised from notable because
the model found its mention of a credential file unexpected.

## 2. Packages

### 2.1 Malicious packages: not measured

- The original plan was to replay the [OSSF malicious-packages](https://github.com/ossf/malicious-packages) records.
  Those are OSV reports (names, versions, descriptions) with no code, so there is nothing for a code reader to read.
- A dataset with code does exist: [DataDog/malicious-software-packages-dataset](https://github.com/DataDog/malicious-software-packages-dataset),
  Apache-2.0. At commit `8a74a4c8ee0e1a2927f0419e0710968702ded609` (16 Oct 2026) it has 1,448 compromised npm versions
  (3.5 GB) and 25,460 malicious-intent npm versions (23.7 GB), each as a zip with the published password `infected`.
  It also has 204 malicious AI skills (19 MB).
- The proposed subset was 50 compromised + 50 malicious-intent versions (one version per package, chosen by SHA-256,
  about 151 MB). The download wasn't approved in this round, so **there is no recall number for malicious packages**.
  `eval/run.mjs` is ready for it (`fetch datadog-npm`, `score datadog-npm`), but that path has only been tested
  against zips built by its own self-test, never against the real samples.

### 2.2 Benign packages: false alarms

The 174 npm packages installed in D:/sloth-test (the dependency tree of `rea-agents@6.7.0`; the lockfile lists 179,
and 5 platform-specific builds aren't installed). They come from the public registry and are assumed benign, not
verified. They lean towards packages that legitimately run programs and open sockets (playwright-core, node-pty,
frida, ws), which makes them a hard benign set.

| | hold | review | notable | info | false alarms (hold or review) |
|---|---|---|---|---|---|
| rules only (before the description rule, Oct 21) | 0 | 18 | 12 | 144 | 18 / 174 = 10.3% |
| rules only (with it, Oct 23) | 0 | 13 | 14 | 147 | 13 / 174 = 7.5% |
| rules only (and fixed commands, Oct 23) | 0 | 12 | 15 | 147 | 12 / 174 = 6.9% |
| rules + model | 0 | 3 | 16 | 155 | 3 / 174 = 1.7% |

The description rule (Oct 23): without the model, a capability a package names in its own description or keywords counts as expected, one step down, the way the model would label it; combinations are never lowered. It took 5 of the 18 off the list (commander, cross-spawn, real-require, tunnel-agent, ws). Most of the 13 left run a fixed command (`ldd --version`) or build validators with `new Function` (ajv and the libraries built on it), and their descriptions don't say so. Skills have no manifest, so the skill numbers above are unchanged.

The fixed-command rule (Oct 23): a program run with a command written out in the code (a string, a const holding one, or a file in the package's own folder) is noted, not queued, unless the command downloads, pipes into a shell, installs, or fetches and runs a package (`npx`, `deno run`). It took detect-libc off this list (13 to 12), and on a real Next.js app (trellient, 428 packages) @tailwindcss/oxide and detect-libc (12 to 10). sharp and update-browserslist-db stay: each also builds a command at run time.

With the model, the three reviews are:

- `ajv` builds code with `new Function()`. Compiling schemas into code is how ajv works.
- `frida` runs an install script that downloads a prebuilt binary. Install-time code is a combination, so the model
  can't lower it.
- `pino` writes files with `writeFileSync()`. A logger writing files is the model's own example of something expected.
  Here it said unexpected anyway.

Rules only, the 18 are packages that use `fetch`, sockets, child processes or `new Function()` for their stated job
(including playwright-core, ws, cross-spawn, isomorphic-git, @zip.js/zip.js, both @modelcontextprotocol packages and
rea-agents).

## 3. Laziness: what a run costs

`node bin/slowship.js D:/sloth-test`, run through `eval/run.mjs lazy`, which uses its own `SLOWSHIP_HOME` under
D:/slowship-eval, so the demo data in D:/sloth-test/.slowship-ui is untouched. A run checks the 174 installed packages
plus the 99 agent skills installed on this machine (273 items). No MCP server here has readable code, so nothing is
fetched.

| run | wall time | items | already known | model calls | model time | code files found | parsed | test/example files skipped |
|---|---|---|---|---|---|---|---|---|
| first run, with model | 319.9 s | 273 | 23 | 51 | 294.3 s | 4,280 | 3,825 | 454 |
| same run again | 2.1 s | 273 | 273 | 0 | 0 s | 0 | 0 | 0 |
| first run, rules only | 29.0 s | 273 | 23 | 0 | 0 s | 4,280 | 3,825 | 454 |
| same run again | 1.8 s | 273 | 273 | 0 | 0 s | 0 | 0 | 0 |

- "Already known" on a first run counts items whose bytes appeared earlier in the same run (the same skill installed
  in two places): each content fingerprint is read once.
- One file wasn't parsed: a 2 MB+ bundle in rea-agents, which slowship skips and reports.
- "Code files" counts JavaScript and the Python/shell scripts in skills. The `.md` files read for instructions
  aren't counted by slowship's coverage, so they aren't here either.
- The model asked about 51 of 250 distinct items: the other 199 had nothing worth judging and got no model call.
  Model time is 92% of the first run.
- A rerun still starts Node, reads the lockfile, hashes every skill folder to spot changes, and loads the cache. That
  is the 2 seconds.

## 4. Scanner gaps found

`src/` was not changed. These are what this evaluation turned up, roughly by how many misses each one explains:

1. **SKILL.md phrase rules are narrow** (20 PI misses). By design they should not cry wolf on documentation, but they
   cover four behaviours out of the benchmark's fifteen.
2. **No rule for "install this prerequisite first"** (15 wild misses): base64 piped into a shell (`echo … | base64 -D
   | bash`), password-protected zips to run, and paste-site scripts. This is the shape of the real-world campaign in
   the sample, and probably the cheapest gain available.
3. **Code in markdown code blocks is never read as code** (8 misses). The script line rules could run over fenced
   `bash`/`python`/`js` blocks in `.md` files.
4. **TypeScript isn't read, and isn't reported as unread** (2 misses). `facts.dirFacts` only looks at `.js`, `.cjs`
   and `.mjs`, and coverage counts only those, so a skill whose only code is `.ts` shows "0 files" instead of
   "1 file not read". This is a coverage-reporting bug: slowship promises to say what it couldn't read.
5. **The script decode rule misses macOS `base64 -D`** (it matches `-d` and `--decode` only; all 9 base64 samples use
   `-D`), and the script rules aren't applied to `.md` files at all.
6. **No rule for bulk file encryption or deletion** (2 ransomware misses).
7. **A combination can't be lowered, even when it is the item's job** (1 false hold on a cron-based auto-restarter,
   plus `frida` at review). That trade is deliberate and worth keeping, but it should be stated in the report.
8. **Examples of attacks in documentation read as instructions** (1 false hold on a security-audit skill).

## 5. Reproduce

From the slowship folder, with Node 22.19 or later. Samples and results go to `SLOWSHIP_EVAL_ROOT`
(default `D:/slowship-eval`). The benign npm project is `SLOWSHIP_EVAL_BENIGN` (default `D:/sloth-test`).

```bash
node eval/run.mjs selftest
```

```bash
node eval/run.mjs fetch malskillbench
```

```bash
node eval/run.mjs score malskillbench
```

```bash
node eval/run.mjs score malskillbench --model
```

```bash
node eval/run.mjs lazy
```

- `fetch` downloads real malware. Run it only in a folder you are happy to keep it in, and never run anything inside
  that folder. Each file's git blob hash is checked against the pinned tree, and the subset is the same every time.
- `score` starts from an empty cache each time and writes every verdict, with findings, to
  `results/<set>-<mode>.json`. Samples that antivirus removed or changed are listed as damaged, not scored.
- `--model` needs Ollama on 127.0.0.1:11434 with `gemma4:e2b`. The runner refuses to report model numbers if the
  model isn't reachable, rather than quietly falling back to rules.
- `lazy` needs an installed npm project. Its numbers include this machine's own agent skills, so they differ by
  machine.
- Packages, if a download is approved: `node eval/run.mjs fetch datadog-npm`, then `score datadog-npm`. The DataDog
  AI skills: `fetch datadog-skills`, then `score datadog-skills` (malicious only, so recall only).
